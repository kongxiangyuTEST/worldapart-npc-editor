# speech_layer 第二轮：从「58 条基线」补到「58 × 48 双层结构」

> 状态：**方案（未开工）** · 2026-10-27 修订
> 依据：`docs/reverse/A1IndexTTSMod-语音契约-权威逆向.md`（从 MOD DLL 内嵌资源抽出的权威数据）
> 前版文档 `speech_layer-V2细粒度tag生成器-可行性方案.md` 的部分结论已被本版推翻，以本版为准。

---

## 一、先承认：我上一版方案指错了地方

上一版我说「缺口是 V2 的 35 个 tag 生成器」。拿到权威数据后，**这是错的**：

1. **V2 的 `tag` 不是白名单枚举**，是「空 或 2–6 个汉字」的**开放描述**（正则 `^(|[\u3400-\u9fff]{2,6})$`）。
   不存在「35 个 tag 的固定清单」——**不需要也不可能去对齐一个清单**。
2. 那「34 项声音事件规则」是**演绎指导文档里给模型的示例**，不是解码器约束。
3. **真正缺的东西在 V1 帧里，不在 V2**：MOD 的 `delivery` 是**两层拼接**，我们只做了第一层。

所以本轮方案的主战场是 **V1 的 delivery 结构**，V2 台本反而是次要的。

---

## 二、真相：delivery 是「角色基线 +；+ 逐句表演」

MOD 台账 4311 条的 `delivery` 全部符合这个结构：

```
成熟从容地招呼客人，前句关照、后句带浅笑，"管够"说得笃定，语速适中。
└────────────────── 逐句表演（48 种之一）──────────────────┘

中等语速，成熟从容，停顿有分寸 ；轻描淡写地自述，语气诚恳，不卑躬屈膝
└──── 角色基线（58 种之一）────┘ └────── 逐句表演（48 种之一）──────┘
```

- **第一层**：`characters[npc_id].delivery` → 1278 角色去重后 **58 条**，中位 16 字
- **第二层**：`entries[].voice_style.delivery` 的「；」后段 → **48 条**，中位 18 字
- **合成**：58 × 48 = **646 种组合**，4311 条全部落在此范围

### 我们的现状

`voicebook.py` 已经**完整收录了第一层 58 条**（做得对）。但：

| 层 | 我们有没有 | 效果 |
|---|---|---|
| 第一层 58 条角色基线 | ✅ 有 | 能保证「同一个 NPC 口吻稳定」 |
| 第二层 48 种逐句表演 | ❌ **没有** | **同一句话，无论什么场合，都是同一句 delivery** |

**这就是「会调 / 不会调」的差距所在**：不是 tag，不是参数，是**同一角色在不同语用场合该有不同的表演**。

完整 48 条：`docs/reverse/performance-profiles.json`

### 注意 top2 的启示

`humble`(1946) + `intro`(979) = **68%**，因为台账主体是「基础招呼 + 自我介绍」——
这两类台词在**预设脚本**里占了绝大多数，但**在真实对话里几乎不出现**。

> **对我们的直接含义**：不能照搬这 48 条的分布权重。真实对话需要的是
> `ask / care / think / serious / warn / refuse / comfort / joke / angry / sad / confess ...`
> 这些「对话态」表演。所以我们要**保留 48 条的结构，但重新配一套对话场景清单**。

## 四、方案：给 voicebook 加第二层

### 4.1 数据结构（对齐官方）

```python
# voicebook.py 新增

# profile -> 角色基线（已有，保持）
PROFILE_DELIVERY = { ... 58 条 ... }

# 新增：performance -> 逐句表演模板（对齐官方 48 条结构，按对话场景重配）
PERFORMANCE_DELIVERY = {
    "neutral":   "以自然语速平实说，重点清楚，不额外加戏",
    "ask":       "重点落在所问之处，句尾轻微上扬，不连续逼问",
    "think":     "边想边说，疑问前自然停顿，不故作高深",
    "care":      "关心落在具体话上，轻柔询问，不演成训斥",
    "serious":   "先把事情说清，句间稍停，重音稳定",
    "warn":      "提醒处稍放慢，危险重点说清，不渲染恐怖",
    "refuse":    "界限说得明确，语尾干脆，不额外挑衅",
    "comfort":   "轻声坦诚，停顿留给对方，亲近而不撒娇",
    "joke":      "略带笑意，转折轻快，包袱处稍停，不故意大笑",
    "sad":       "轻叹般收住语尾，情绪说清，不演成号哭",
    "angry":     "压着怒气仍保持礼貌，落字加重，不吼叫",
    "confess":   "关键心意放慢说清，停顿自然，不夸张煽情",
    "memory":    "谈旧事稍放缓，转折留白，情绪收着说",
    "request":   "请求说得直接有礼，末尾给对方回应空间",
    "casual":    "像熟人随口闲聊，语尾放松，起伏自然",
    "teach":     "解释清楚，步骤分明，提醒不训人",
    "trade":     "自然谈货物与条件，关键要求清楚，不叫卖",
    "respect":   "称呼清楚有礼，语气稳当，不夸张奉承",
    "wary":      "音量稍收，重点明确，保持戒心不急促",
    "excited":   "语气明亮，细节处有兴致，不连声感叹",
    # ...（共约 25-30 条，覆盖真实对话）
}

def compose(profile: str | None, performance: str | None) -> str:
    """合成两层 delivery：基线；表演"""
    base = delivery_for(profile)              # 第一层（已有）
    perf = PERFORMANCE_DELIVERY.get(performance or "neutral",
                                    PERFORMANCE_DELIVERY["neutral"])
    return f"{base}；{perf}"
```

**关键：`compose()` 用「；」连接，与官方格式完全一致。**
这样 MOD 解出来的字符串形态与它自己生成的**一模一样**，Breeze 的处理不会跑偏。

### 4.2 `performance` 从哪来？

三条路，从低风险到高收益：

#### 路线 A（P0，零模型依赖）：按「回复类型」硬映射

游戏 NPC 回复前，proxy 层**能看到本轮 prompt 的 `talk_type`**（A1TalkType: first_talk / player_talk / passive_talk / summary）。
再结合「本轮是否含问号 / 是否含拒绝词 / 玩家上一句情绪」做**轻量规则判定**：

| 判据 | performance |
|---|---|
| 含「？」且是回应玩家提问 | `ask` |
| 玩家上句含负面词（怒/骂/滚） | `wary` 或 `angry` |
| 含拒绝词（不/别/恕难/不能） | `refuse` |
| 含宽慰词（别怕/无妨/我在） | `comfort` |
| 台词长度 > 60 字 | `serious` |
| 其他 | `neutral` |

**优点**：完全确定性、零成本、可解释、可回退。
**缺点**：粗糙，只能抓最明显的语用类型。

#### 路线 B（P1，让模型自己标）：注入时要求输出 `performance`

在 `tts_style_prompt_v1.txt` 里加一句：

```
- delivery 请写成「角色说话习惯；本句表演方式」两段，用中文分号「；」分隔。
  前段描述这个角色一贯的说话方式，后段描述这一句具体的语速、停顿、重音、句尾变化。
```

**优点**：语义最准，模型最懂自己这句想怎么演。
**缺点**：小模型可能不遵守两段格式 → 需要 normalize 兜底（只取后段/只取前段/整体当一段）。

#### 路线 C（P2，混合）：A 定基调，B 补细节

先用 A 算出 `performance`，作为**提示词里的建议**给模型：

```
本轮建议表演类型：care（关心落在具体话上，轻柔询问，不演成训斥）
请在此基础上按这句的实际内容微调。
```

模型若给出合规的两段式就用它的，否则回落到 A 的硬映射。

### 4.3 必须做的规整（normalize）

无论哪条路线，解码侧都要兜：

```python
def normalize_delivery(d: str, profile: str | None) -> str:
    """保证 delivery 是合规的「基线；表演」两段式，且不超 80 字。"""
    d = (d or "").strip()
    if "；" in d:
        head, tail = d.split("；", 1)
        # 若前段明显不是基线（太短/不是角色口吻），用我们的基线替换
        if len(head.strip()) < 6:
            head = delivery_for(profile)
        out = f"{head.strip()}；{tail.strip()}"
    else:
        # 模型只给了一段 → 补上基线
        out = f"{delivery_for(profile)}；{d}" if d else delivery_for(profile)
    return out[:DELIVERY_MAX]   # 80 字硬截断
```

> **为什么要硬限 80 字**：`DELIVERY_MAX = 80` 是我们 `contract.py` 的既有约束，
> 与官方「一句简短中文」一致。两段式容易超长，必须截。

## 五、顺带要修的三处（基于权威数据）

### 5.1 注入提示词补一句官方原话

官方注入里有这句我们没抄的关键句：

> 本轮上下文中的角色卡、speakStyle、toneStyleDesc 及其他说话要求，已经是决定这句台词与表演方式的依据。
> **下游不会再补上人物口吻预设**；不要只输出脱离角色的情绪名称，也不要重复抄写整张角色卡。

这句是**专治「名片注入后模型把口吻写成通用情绪」**的。应加进 `tts_style_prompt_v1.txt`。

### 5.2 intensity 上限应该压低

权威数据：4311 条台账 **max = 0.55，中位 0.2，从未用过 0.8**。

我们的注入现在没给上限建议 → 模型容易写 0.7/0.8。应改成：

```
- intensity：0 到 1 的数字。日常对话请用 0.15–0.35；情绪明确时 0.4–0.55；
  仅真正的冲突/爆发场景才可超过 0.6。绝大多数正常台词应在 0.2 附近。
```

### 5.3 `emotion_tags` 应当更收敛

权威 Top2「平静」(2187) +「谦和」(1946) = **48%**。官方风格是**极克制**。

我们的台账/注入若鼓励模型写「压抑的愤怒」「带着担忧的安抚」这类长标签，会**偏离官方分布**。
建议：**主标签优先用高频词表**（平静/谦和/温和/认真/审慎/好奇/坚定/自信/沉着/关切…74 词），
次标签才放开。这不影响表达力，只影响「像不像原版」。

## 六、分期与风险

| 期 | 做什么 | 依赖 | 风险 |
|---|---|---|---|
| **P0** | `PERFORMANCE_DELIVERY` 词表 + `compose()` + `normalize_delivery()` + 路线 A 规则映射 | 无 | 低。规则粗糙但确定性 |
| **P1** | 注入提示词改成两段式要求 + 路线 B | 模型遵守度 | 中。小模型可能不遵守，靠 normalize 兜 |
| **P2** | 路线 C 混合（建议 + 模型微调） | P0+P1 | 中 |
| **P3** | V2 台本 `segments[].tag` 生成（2–6 汉字开放描述） | 无，但优先级低 | 低。tag 开放，不需对齐清单 |

### ⚠️ 不承诺的事

1. **这不是「让声音变真人」**。58×48 提升的是**文本表演的层次感**，声音质感仍在 TTS 模型 + 参考音（用户已配好 1169 项）。
2. **不保证模型会听话**。两段式格式依赖模型配合，所以 P0 的规则映射是**兜底地基**，不能跳。
3. **不照搬台账的 48 条权重**。`humble`+`intro` 占 68% 是因为台账多为预设招呼，真实对话要重配。
4. **未解密 `.enc` 契约**。字段定义已由 schema + 提示词覆盖，不影响实现。

## 七、需要你拍板

1. **P0 做不做**？（词表 + compose + normalize + 规则映射，纯确定性，不依赖模型）
2. **performance 词表配多少条**？我倾向 **25–30 条**覆盖对话场景（官方 48 条里有一半是预设招呼专用，用不上）。
3. **要不要走 P1**（改注入让模型自己标两段式）？这是收益最大但最依赖模型配合的一步。
4. **V2 台本 tag 还做不做**？tag 是开放描述（2–6 汉字），做起来比原以为的简单，但优先级应低于第二层 delivery。
