# 提示词编排数据化研究（「预设」这块硬骨头）

2026-10-30。**只做研究，不动代码**。结论先给：难点不是格式，是「改完必须一字节不差」。

---

## 0. 结论

1. 我们现在**已经有一套隐式的「提示词编排」**——7 个注入层、固定顺序、写死在 `prepare_messages()` 里。所以「预设」不是从零做，而是把已有的东西**从代码搬进数据**。
2. 搬得动，前提是做一层「块渲染器」，且默认配置下的输出必须与现在**逐字节相同**。
3. 酒馆预设**搬不全**：它假设上下文由 ST 自己拼，而我们的 system 是游戏给的固定 10 段结构。导出的 preset 只能复现「我们加了什么 + 相对顺序」，复现不了「游戏原本有什么」。
4. 真正的工作量在**回归**，不在功能：212 条真实样本的等价性验证，才是这件事能不能做成的判据。

---

## 1. 现状：其实有 7 层，顺序是实测调出来的

`prepare_messages()`（core_proxy.py:1449）里的执行顺序，每一步都有历史原因：

| # | 层 | 函数 | 数据源 | 落点 | 预算 / 开关 | 幂等 |
|---|---|---|---|---|---|---|
| 1 | 替换规则 | `apply_rules_to_messages` | `ai_config.rules`（12 条） | 只改**原始 system** | 文本/正则两种 mode | — |
| 2 | 合并 system + 注入语 | `rewrite_messages`（:1104） | `ai_config.inject`（495 字） | 注入语放在**最前** | `proxy_passthrough` 总闸 | — |
| 2b | 强制角色交替 | `fix_alternation` | — | 非 system 消息 | — | — |
| 3 | 长期记忆 | `inject_memory_to_messages` | `memory/<id>.json` | append 到 system 末尾 | `memory_budget` 800 / `save_guard` | 每条事实去重 |
| 4 | 世界信息 | `inject_lorebook`（:2183） | `lorebook.json` | append（`## 世界信息（补充设定）`） | `lorebook_budget` 800 / 关键词命中 | 按 priority 排序 |
| 5 | 玩家设定 | `inject_persona`（:2231） | `ai_config.persona` | append（`## 玩家设定…`） | 2000 字截断 | — |
| 6 | 用户名片 | `inject_user_card`（:524） | `editor_cards/<id>-<名>.md` | append（`## 角色演绎要求…`）**放最后** | `inject_user_card` | 每卡一份 |
| 7 | TTS 风格 / 台本 | `speech_layer.inject_tts_style/script` | `tts_style_prompt_v1.txt` 等 | 追加到 system | `tts_style_inject` / `tts_script_v2` | `A1_TTS_STYLE_V1` 等标记 |

三个必须记住的性质：

- **除了第 1 层，其余全是「追加到 system 末尾」**（`_append_system_text`，:2148）。所以顺序 = 权重，越靠后越能盖住前面。名片放最后是实测结论：放前面会被游戏的「任务 / 输出格式 / 本轮状态」盖住。
- **第 2 层（注入语）是唯一放最前的**，因为它要压住游戏原生的「你是 AI 助手」类设定。
- **第 7 层靠文本标记去重**，模板文案一改标记就失效 → 重复注入。这是数据化时最容易踩的坑。

## 2. 为什么酒馆预设搬不过来（关键判断）

酒馆的 preset 是**渲染器指令**：

```json
{
  "temperature": 0.9, "top_p": 1.0,
  "prompts": [
    {"identifier": "main", "name": "主提示", "role": "system", "content": "…", "enabled": true},
    {"identifier": "worldInfoBefore", "name": "世界书(前)", "marker": true},
    {"identifier": "charDescription", "name": "角色描述", "marker": true},
    {"identifier": "chatHistory", "name": "对话历史", "marker": true}
  ],
  "prompt_order": [{"character_id": 100000,
                    "order": [{"identifier": "main", "enabled": true}, …]}]
}
```

它描述的是「**ST 渲染上下文时，按这个顺序把各来源塞进去**」。

我们的现实是：**上下文是游戏拼好的**，10 个段落（角色设定 / 说话习惯 / 当前场景 / 过往要事…）由游戏代码按顺序写入，我们只能在末尾追加。所以：

| 想表达 | 酒馆 preset 能表达吗 |
|---|---|
| 我们加了哪 5 块、相对顺序 | ✅ 能 |
| 采样参数 | ✅ 能 |
| 游戏原生那 10 段的存在与顺序 | ❌ 不能（preset 里没有「游戏」这个概念） |
| 「名片必须在最后才有权重」这条约束 | ⚠️ 只能靠注释说明，preset 格式本身不校验 |

**所以「预设导出」的正确定位**：把我们的风格层搬到别的平台复现「说话感觉」，**不是**复现游戏。这一点必须写在功能说明里，否则用户会以为导出的 preset 能在酒馆里跑出一样的剧情。

## 3. 块模型设计（把代码搬进数据）

目标：一次重构，两个出口——本地渲染（替代硬编码）+ 导出 ST preset。

```jsonc
{
  "id": "user_card",              // 唯一键，也是 ST 那边的 identifier
  "kind": "card",                 // rules|inject|memory|lorebook|persona|card|style
  "enabled": true,
  "order": 60,                    // 稀疏整数，留空位插入
  "anchor": { "type": "append" }, // append | after_section | depth
  "source": { "type": "npc_card", "field": "user_card" },
  "budget_chars": 0,              // 0 = 不限
  "template": "\n\n## 角色演绎要求（优先于以上所有属性与场景描述）\n{{content}}\n\n以上每条都是硬性要求…",
  "idempotent_marker": "",        // 非空时先查系统里有没有这个标记
  "priority_note": "必须最后：离生成位置最近，权重最高"
}
```

映射到现有 7 层（默认值就是现在的行为）：

| id | kind | order | anchor | 备注 |
|---|---|---|---|---|
| `rewrite_rules` | rules | 5 | whole_system | 只作用于原始 system，不进 append 链 |
| `inject_prefix` | inject | 10 | prepend | 注入语，唯一前置 |
| `memory` | memory | 30 | append | budget 800 |
| `lorebook` | lorebook | 40 | append | 关键词命中才出 |
| `persona` | persona | 50 | append | 2000 字截断 |
| `user_card` | card | 60 | append | **必须最后** |
| `tts_style` | style | 70 | append | 幂等标记 |

两个设计要点：

1. **`anchor` 现在只需要 `append`**，但 `after_section`（插到「## 说话习惯」后面）留好口子——历史上试过，效果不好但可能再试。
2. **模板与标记分离**：`template` 变了不影响 `idempotent_marker`，避免「改文案 → 重复注入」这个坑（现在的实现是标记嵌在文案里）。

## 4. 等价性回归：真正的工作量

### 语料

`prompt_samples/` 共 237 条，其中 **212 条是对话类**（含「## 角色设定」），其余 25 条是记忆压缩请求（必须原样透传，任何层都不许碰）。角色覆盖：纪小蝶 110、纪澜之 41、苏倾盏 16、章籽梦 15、荀迟 6、索雅 5。

### 方法

```
for sample in 212:
    A = copy(sample); prepare_messages(A)          # 老路径
    B = copy(sample); blocks.render(B, cfg=default) # 新路径
    assert json.dumps(A["messages"]) == json.dumps(B["messages"])
```

### 三个会让比对假阳性的陷阱

1. **`save_guard` 有副作用**：`inject_memory_to_messages(persist=True)` 会写盘，跑两遍结果不同 → 回归必须 `dry_run=True`。
2. **记忆每轮 `age_count +1`**：同一份 memory 跑两次，第二次的命中结果会变 → 回归要复制 memory 目录到临时目录。
3. **时间/顺序敏感字段**：`_remember_npc` 写 `last_npc.json`、日志行数统计——这些不进 messages，但别混进比对。

通过标准：212/212 字节相同；再抽 3 条把最终 payload（含 temperature 等）整体比对一次。

### 为什么要这么严

因为这条路一旦有 1 个字符的偏移，游戏的**前缀缓存**就会全部失效（成本差 50 倍），而且现象是「变慢 + 变贵」，不会报错。人眼看不出来。

## 5. 与 ST 预设的字段映射

| 我们的块 | ST 里最接近的 | 处理 |
|---|---|---|
| `inject_prefix`（注入语） | `main`（主提示） | 直接映射，role=system |
| `user_card`（名片） | 无对应 | 导出成自定义 prompt 块，`role=system`，排在 `chatHistory` 之前 |
| `memory` | `worldInfoAfter` 或 `at_depth` 条目 | 二选一，需实测哪种在 ST 里更稳 |
| `lorebook` | `worldInfoBefore` | 我们也是关键词触发，结构最接近 |
| `persona` | `personaDescription` | 直接映射 |
| `rewrite_rules`（12 条替换） | ST 的 regex 扩展 | 格式不同，只能逐条导出成说明文档 |
| `tts_style` | 无 | 导不出去，ST 没这个概念 |

## 6. 风险清单

1. **顺序即权重**：数据化之后有人在配置里拖错一格，行为会静默变化。→ 编排页必须显示「最终 system 的段落顺序预览」，而不是只显示块列表。
2. **前缀缓存**：顺序、模板任一变动都会打掉缓存。→ 保存前提示「改动会影响缓存命中」，并给出改动前后的 hash。
3. **幂等标记漂移**：现在的标记写在文案里。→ 数据化时把标记独立成字段。
4. **双路径并存期**：至少要留一个 `--legacy` 开关的版本，出问题能立刻切回。
5. **212 条样本只覆盖 6 个角色**：其余 1586 张卡没有样本。→ 回归通过后再加一轮「全量卡 × 合成请求」的结构比对（不比对内容，只比对段落顺序与块是否存在）。

## 7. 建议排期（4 步，按风险从高到低）

| 阶段 | 内容 | 判据 |
|---|---|---|
| S1 | 块模型 + 渲染器 + 回归脚本，默认配置下替代 `prepare_messages` | 212/212 字节相同 |
| S2 | 编辑器「编排」页：拖顺序、开关、预算、最终 system 预览 | 改配置后能立即在预览里看出段落变化 |
| S3 | 预设导出（含「这只是风格复现」的说明）+ 世界书导出 | 导出物能在 ST 里导入不报错 |
| S4 | 观察一周后删旧路径 | 无回退需求 |

S1 是全部前置：没有字节级等价，后面三步都是空中楼阁。

## 7.5 需求澄清后的结论（2026-10-30 追加）

用户明确：**只要导出，不需要导入，也不需要反过来驱动自己的拼装**。

因此本文第 3～4 节（块模型 + 字节级回归）**暂不执行**——那是"让注入层可配置"才需要的。
导出方向改用固定层表（`tools/tavern_export.py`）直接生成 preset，成本半小时，
代价是**层顺序仍写死在代码里**：以后要调顺序还是得改 `prepare_messages()`。

什么时候回头做 S1：当出现「想在编辑器里拖顺序」或「想让世界书驱动注入」的需求时。
届时本文第 4 节的回归方案与三个假阳性陷阱可以直接照做。

## 8. 一句话给决策

如果只想「能导出点东西给别人用」，那第 5 节的映射表足够，半天能做完，但价值有限——因为它不能反向影响游戏。
如果要「自己也能改编排顺序」，就必须走 S1，那是一天起步的重构，收益是**注入层从此可配置**，不再每次调顺序都改代码。
