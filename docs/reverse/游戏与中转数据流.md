# 游戏 ↔ 中转 数据流 + MOD 语音合成全景

> 2026-10-28 求证。依据：游戏 `il2cpp_dump/dump.cs`（78MB）+ MOD `A1IndexTTSMod.dll` 字符串池。
> 凡属推断的地方都标了「推断」，实测过的标「已验证」。

---

## 第一部分：游戏和中转之间到底怎么传数据

### 1.1 请求方向（游戏 → 我们）

游戏侧的配置结构（`JNGame.Ainpc.Llm.LlmSettings`）：

```
LlmMode   Mode        // Official=0 / Custom=1
string    BaseUrl     // 我们这里填 http://127.0.0.1:8788
string    ApiKey
string    Model
float     Temperature
int       MaxTokens
Dictionary<string,string> ExtraHeaders
JObject   ExtraBody
```

`Mode = Custom` 时，游戏把 `BaseUrl` 指向 Caddy(8788) → core_proxy(8789)。
这就是**我们唯一的接入点**：一个标准 OpenAI 兼容的 `/v1/chat/completions`。

请求体是普通 messages 数组，system 里是游戏拼好的整段 prompt
（`## 角色设定` / `## 角色背景` / `## 说话习惯` …）。
我们的注入全部发生在这一段上。

### 1.2 响应方向（我们 → 游戏）—— 关键在这里

游戏解析回复用的是 `OpenAiCompatProvider.Complete`，它返回：

```csharp
public sealed class LlmResult {
    public bool   Success;
    public string Content;        // ← 只有这一个字符串字段，没有结构化扩展
    public LlmError Error;
    public long   HttpCode;
    public string RawError;
    public int    PromptTokens;
    public int    PromptTurnId;
    public string FinishReason;
    ...
}
```

**`LlmResult` 里只有 `Content` 一个字符串**，没有任何字段能装 `a1ttsv2`。
也就是说：游戏不解析我们的扩展字段，它只是把 `choices[0].message.content`
**原样当成一个字符串**收下。

然后进到 `NpcModel.ChatReply`：

```csharp
private struct NpcModel.ChatReply {
    public string Display;         // 拿去显示的文本
    public string RawEnvelope;     // ← 原始信封（整个 JSON 字符串）
    public int    RelationTurnId;
    public bool   Blocked, Rejected, KeepOutOfHistory;
}
```

`Display` 是从 `RawEnvelope` 里抽出来的展示文本；
`RawEnvelope` 保留**整段原始字符串**。

再往下走：

```csharp
public void AddNpcChatMessage(string messageText, string npcRawOutput, int promptTurnId = -1)
```

**`npcRawOutput` 就是 `RawEnvelope`** —— 也就是我们返回的那整段 JSON 文本，
`a1ttsv2` 原封不动躺在里面。

### 1.2.1 我们实际发出去的是什么形状

我们的代理返回的 `content` **不是字符串，是一个 JSON 对象**：

```python
outer = {
  "choices": [{
    "message": {
      "role": "assistant",
      "content": inner,      # ← dict，不是 str
    }
  }]
}
```

其中 `inner` 形如：

```json
{ "content": "台词……", "emotion": "平静",
  "control": "none", "observe": {...}, "intent": {...},
  "a1ttsv2": { "instruct": "...", "segments": [...] } }
```

游戏拿到的是一个 JToken 对象，它要落成 `LlmResult.Content`（string）
必然经过一次**序列化**。序列化会保留所有键，包括 `a1ttsv2`。

所以这条路是：**我们发对象 → 游戏序列化成字符串 → RawEnvelope → npcRawOutput**。
整条链上没有任何一环做字段过滤。

### 1.3 所以字段能活到 MOD 手里吗？

**能，前提是它走的是 `RawEnvelope` 这条路。** 依据：

| 环节 | 机制 | 我们字段的命运 |
|---|---|---|
| `LlmResult.Content` | 纯字符串，不解析 | ✅ 原样保留 |
| `ChatReply.RawEnvelope` | 存整段原始字符串 | ✅ 原样保留 |
| `AddNpcChatMessage(npcRawOutput)` | MOD 钩子收到 | ✅ 到手 |

### 1.4 但有一个真实的丢字段风险

`HistoryEnvelope` 里有个方法很可疑：

```csharp
public static string NormalizeOrWrap(string rawResponse, ChatMode mode)
private static void CopyIfPresent(JObject from, JObject to, string key)
```

`CopyIfPresent(from, to, key)` 是**按白名单逐个复制字段**。
如果游戏用这个方法重建信封，那么 `a1ttsv2` 这种非白名单字段就会被丢掉。

不过要注意：它重建的是**写进对话历史的信封**（要回喂给 LLM 的那份，
只该有 content/emotion/control 这些游戏认识的字段），
和我们讨论的 `npcRawOutput` 不一定是同一份。

而且 MOD 自己钩了 `OnPreGameReplyNormalization`（**归一化之前**），
说明 MOD 的作者也知道归一化会动数据，所以提前抓。

**结论：大概率能活，但必须实测。** 这就是为什么开了 Stage2A 捕获。

### 1.5 MOD 作者自己怎么说

DLL 里有一段中文说明，是它自己的免责声明，非常关键：

> 游戏内捕获文本不等于供应商原始 HTTP 回包。更早网络层未观测；
> **WorldApartPersonaMod/BuiltinServer 的 C# 观察钩子仅覆盖该托管代理，
> 不覆盖独立 Python 代理内部。**

**这直接证实了：MOD 的钩子够不到我们的代理内部。** 它只能看到游戏愿意交给它的东西。

这也解释了另一件事：MOD 的「提示增强」（往 prompt 里加 `a1ttsv2` 要求）
对我们是**失效**的 —— 它增强的是游戏自己拼 prompt 的那条路径，
我们收到的是游戏原始 prompt（59 个样本 0 个含 a1ttsv2 就是证据）。

而 `IsOfficialTransport` / `PatchProxyReplyEvidence` / `ObserveProviderReply`
这几个方法名说明：MOD **知道**有「官方传输 vs 自定义传输」的区别，并对两者分别处理。

## 第二部分：MOD 的语音合成全景

### 2.1 从方法名还原的完整管线

```
[游戏回复到达]
      │
      ▼
OnPreGameReplyNormalization (Prefix)     ← 归一化之前抓原始回复
      │
      ▼
ExtractNpcReply / OnNpcReply              ← 取出 NPC 回复
      │
      ▼
A1TtsV2ScriptParser.Parse                 ← 解析 a1ttsv2
      │  ├─ ScriptAliases / SegmentAliases ← 字段别名归一
      │  ├─ A1TtsV2FormatRepair           ← 格式坏了先修
      │  └─ 失败 → RejectedReplyScript / RejectedReply
      ▼
A1TtsV2Script { Instruct, Segments[] }    ← 解析结果
      │
      ├─ 解析失败 → PresetV2Scripts       ← 回落到预设招呼库
      │              （1591 条，每条自带 a1ttsv2）
      ▼
CanSpeakReply                             ← 判断能不能念
      │
      ▼
ResolveTtsAsync                           ← 决定用哪个引擎/音色
      │
      ▼
SynthesizeAsync                           ← 合成
      │   ├─ BreezeAudioCpp / BreezeSynthesis / BreezeRequest
      │   ├─ BreezePromptContract           ← 提示契约
      │   └─ BreezeChunkPlanner             ← 长文本切块
      ▼
SynthesizeAndPlayAsync → DecodedWav       ← 播放
      │
      ▼
TtsPlaybackSnapshot / LastSynthesis       ← 记录
```

### 2.2 关键类（都在 DLL 里确认存在）

| 类 / 方法 | 作用 |
|---|---|
| `A1TtsV2ScriptParser` | 解析 `a1ttsv2` |
| `A1TtsV2FormatRepair` / `A1TtsV2RepairResult` | 格式修复（`ScriptAliases` / `SegmentAliases` 做别名归一） |
| `A1TtsV2Script` / `A1TtsV2Segment` | 脚本模型（`Instruct` / `Segments[{Text,Tag}]`） |
| `PresetV2Scripts` | 预设招呼库回退（`base_greeting` / `topic_opening`） |
| `CanSpeakReply` | 决定说不说 |
| `BreezeAudioCpp` / `BreezeSynthesis` / `BreezeRequest` | Breeze 合成链路 |
| `BreezeChunkPlanner` | 长文本切块 |
| `BreezeInput` | 实际发给 Breeze 的 `input` |
| `TtsRequestJson` | 请求体诊断快照 |

### 2.3 关掉声音的地方（按顺序）

只要任何一环失败就不出声：

1. `a1ttsv2` 不存在 → `no_spoken_line`
2. JSON 非法 → `a1ttsv2_json_invalid`
3. 字段不对 → `a1ttsv2_unexpected_or_missing_fields`
4. `instruct` 空 → `instruct_blank`
5. `instruct` 过长 → `instruct_too_long`
6. `segments` 空 → 无台词
7. `tag` 超 6 字 → `segment_*`
8. `CanSpeakReply` 判否
9. Breeze 服务没起来 → `Breeze synthesis has no input.`

`last-error.json` 记的那次是第 1 类：**缺少有效 a1ttsv2 台本，未从正文补写**。

### 2.4 一个重要的补充发现

MOD 的预设招呼库（`PresetV2Scripts`，1591 条）**每条都自带完整的 `a1ttsv2`**：

```json
{
  "key": "base_greeting:100000:1",
  "npc_id": 100000, "npc_name": "苏倾盏",
  "source": "base_greeting", "source_id": "1",
  "text": "今日有何事？",
  "speech_policy": "speak",
  "a1ttsv2": {
    "instruct": "保持参考声线。平和询问来意，句尾自然上扬，留出回答的余地。",
    "segments": [ { "text": "今日有何事？", "tag": "" } ]
  },
  "voice_style": { "emotion_tags": [...], "delivery": "...", "intensity": 0.15 },
  "actor_profile": "hostess", "performance_profile": "ask"
}
```

注意 `actor_profile` / `performance_profile` 这两个字段 ——
**和我们现在做的双层结构完全一致**（我们叫 profile / performance）。

`speech_policy` 只在预设库里出现，**回复本身不需要这个字段**。

### 2.5 含义

即使 LLM 一个字都不吐 `a1ttsv2`，MOD 也有兜底：**回落预设招呼库**。
但那只覆盖「开场招呼 / 话题开场」，覆盖不了自由对话。

所以现状是：**NPC 只在说预设招呼时可能有声，正常对话永远静音。**

## 第三部分：现在的判断和下一步

### 3.1 链路可信度

| 环节 | 结论 | 依据强度 |
|---|---|---|
| 我们能把 `a1ttsv2` 写进返回 JSON | ✅ 已验证 | 单测 + 实调 |
| 游戏把它当字符串存进 `RawEnvelope` | ✅ 代码结构确认 | `LlmResult.Content` 是 string |
| `npcRawOutput` = `RawEnvelope` | 🟡 强推断 | 结构 + 命名，未实跑 |
| MOD 能解析出来 | 🟡 强推断 | 有 parser + 别名归一 |
| MOD 传给 Breeze 的 instruct | 🔴 未知 | 请求键列表里没见到 |
| Breeze 会念 | ✅ 已验证 | 手动调用出 6.16s 音频 |

### 3.2 唯一还没排除的风险

`HistoryEnvelope.CopyIfPresent` 的白名单如果也用在 `npcRawOutput` 上，
我们的字段就被洗掉了。**Stage2A 捕获能一次性判定**（已开启，等实跑）。

### 3.3 即使通了，还有一个降级风险

之前实测发现：Breeze 的 `instruct` 必须放 `options.instruct`，放顶层被静默忽略。
而 MOD 的请求体键列表里没看到 `instruct`。

如果 MOD 走的是「顶层层级传 instruct」或「根本不传」，
那么 NPC 会出声，但**语气控制失效** —— 所有台词都用同一套平铺语气念。

这个也能用 Stage2A 的 `TtsRequestJson` 字段确认。

# 附：2026-10-28 实机实测结果 —— 链路通了

## 一、结论

**我们的台本确实传到了 MOD，NPC 确实出声了。**

实测一轮游戏（NPC 100121，翡翠阁主），3 轮对话：

| 轮 | 玩家说 | 台本状态 | 游戏归一化后 | 最终生效 |
|---|---|---|---|---|
| 1 | 你好 | `valid` | `absent` | **`valid`** |
| 2 | 最近在干吗 | `valid` | `absent` | **`valid`** |
| 3 | 来看你便是紧事 | `valid` | `absent` | **`valid`** |

生成音频 2 段：`reply-000003.wav`（19.36s）、`reply-000004.wav`（16.32s），
均为 24000Hz 单声道。`last-error.json` 没有新增错误（还停在 10-25 那次）。

## 二、最有价值的发现：游戏确实会洗字段，但 MOD 会捞回来

看这一列对比：

```
台本状态      valid      ← MOD 在归一化之前抓到的（OnPreGameReplyNormalization）
游戏归一化后  absent      ← HistoryEnvelope.CopyIfPresent 白名单把 a1ttsv2 丢了
最终生效      valid      ← MOD 从原始回复里恢复（recoveredA1ttsv2Status=valid）
```

这印证了之前的推断：`CopyIfPresent` 白名单**确实会丢我们的字段**。
但 MOD 有两条恢复路径：

- `mappedA1ttsv2Status` —— 从游戏映射后的信封里取（这里是 `absent`）
- `recoveredA1ttsv2Status` —— 从原始回复里重新解析（这里是 `valid`）
- `effectiveA1ttsv2Status` —— 最终用哪个，取到了 recovered 的

**所以 MOD 的设计是「映射失败就回原始回复重新解析」，正好绕过了白名单问题。**
这不是我们的功劳，是 MOD 本身够健壮。

## 三、数据格式（编辑器读取用）

```
.state/stage2a/<会话ID>/events.jsonl
```

JSON Lines，每行一个事件（`{utc, seq, pid, record}`）。`record.kind` 的类型：

| kind | 有用字段 |
|---|---|
| `player_input` | `text`（玩家说的话）、`npcId` |
| `llm_content_before_game_reply_mapping` | `a1ttsv2Status`、`voiceStyleStatus`、`a1ttsv2FailureReason` |
| `npc_reply_raw_observation` | `mappedA1ttsv2Status`、`recoveredA1ttsv2Status`、`effectiveA1ttsv2Status` |
| `llm_content_repeat_check_result` | `isRepeated` |

⚠ `CaptureFullPrompt = false` 时 `record.raw` 是 `null`（只存 length + sha256）。
想看回复原文必须把 `CaptureFullPrompt` 也设成 true —— 但那会存下游戏对话内容。

## 四、还剩一个未知项

**`instruct` 有没有真的传给 Breeze，还是没验成。**

原因：`TtsRequestJson` 只存在于游戏内诊断面板，不落盘；
audiocpp 服务端配置 `log_request_body = false`，所以日志里只有请求大小（604 字节）
没有请求体。

要验证只有两条路：

**路线 A：看游戏内 MOD 面板**（零风险，推荐）

面板上这几栏（从 DLL 提取的确切标签）：

```
最终台本
  instruction：      ← 解析出来的 instruct（应该等于我们兜底写的那句）
  segments：         ← 逐段 text + tag
  最终实际朗读正文：

后端：               ← breeze2
参考音：             ← 该 NPC 的 wav
实际 instruction：    ← 真正发出去的 instruct
请求：               ← 完整请求体
```

判断方法：
- 「最终台本 → instruction」显示 `话少干脆，落字有力，语气不绕弯；…`
  → 说明我们的两层合成**进了台本**
- 「实际 instruction」也是同一句 → 说明**传到 Breeze 了**
- 「实际 instruction」是空的 / 是默认的 "Speak clearly and naturally."
  → 说明 **MOD 没有转发**，语气层白做

**路线 B：拦截 8892 端口**

把 audiocpp 换到 8893，在 8892 起一个转发日志，就能录下 MOD 的完整请求体。
但 `BreezeStreamingEnabled=true` 时走 SSE 流式，转发要处理流式响应，
实现成本比 A 高，非必要不用。

如果 instruct 没传，表现是：**NPC 会出声，但所有台词都是同一种平铺语气**。
用户实机听感可以直接判断 —— 如果语气跟着情绪变了，就是传过去了。

## 五、当前生效状态

# 附二：谁让 NPC 出声的？—— 是我们的兜底，不是模型

## 关键事实

实测时 `ai_config.json` 里：

```
tts_script_v2      = 未设置 → 默认 False   ← V2 台本要求注入是关的
tts_style_inject   = 未设置 → 默认 True
```

而且 V1 模板（`tts_style_prompt_v1.txt`）里**一个字都没提 a1ttsv2**，
只要求模型输出 `<a1tts_v1>` 帧。

那 `a1ttsv2Status` 怎么还是 `valid`？

**当时的答案我写的是「命中兜底」—— 这个结论错了**（见下方「附三」的实测更正）。

真实情况：MOD 自己的提示增强**一直在注入 a1ttsv2 契约**（`injectionApplied: true`），
模型是按那份契约输出的，不是我方兜底造的。

那个兜底没有挂任何开关：

```python
if isinstance(inner, dict) and "a1ttsv2" not in inner:
    sl.fill_a1ttsv2(inner, profile=_prof, performance=_perf)
```

所以完整链路其实是：

```
模型输出 content（可能带 <a1tts_v1> 帧，也可能不带）
      ↓
我们 normalize_response 取出 content
      ↓
发现没有 a1ttsv2  →  fill_a1ttsv2 用台词语义现造一段
      ↓  instruct = compose(角色基线, 逐句表演)
      ↓  tag      = tag_for(perform)
      ↓
返回给游戏 → MOD 收到 → a1ttsv2Status=valid → 合成 → 出声
```

## 这代表什么

**好消息**：就算模型永远学不会输出台本，NPC 也能出声 —— 兜底能扛住。
实测 3 轮全部 `valid`，说明这条兜底路径稳定。

**代价**：台本是「按规则造的」，不是「模型理解的」。
质量上限受限于 `perceive()` 的判定准确度，比模型自己写要粗糙。

**所以两个开关的分工**：

| 开关 | 作用 | 建议 |
|---|---|---|
| `tts_script_v2`（默认关） | 让模型自己写台本，台词断句和 tag 更贴合语义 | 想要质量就打开 |
| 兜底 `fill_a1ttsv2`（无开关，常开） | 模型没写时用规则补 | 保底出声，不建议关 |

## 本次该 NPC 的兜底内容

NPC 100121「翡翠阁主」→ 卡片个性 `务实坚韧` → profile `hard`：

```
话少干脆，落字有力，语气不绕弯；以自然语速平实说，重点清楚，不额外加戏
```

**如果 MOD 把 instruct 传给了 Breeze，这个角色说话应该明显偏「短、硬、干脆」。
用户听感可以直接验证** —— 如果语气平淡无个性，就是 instruct 没传过去。

# 附三：2026-10-28 用户导出 TTS 诊断报告后的更正

## 一、更正：台本是模型写的，不是我们兜底造的

用户从游戏内 MOD 面板导出了 `report-20261027T163257824Z.json`，
其中 `promptEvidence` 显示：

```json
{
  "injectionApplied": true,
  "requestMode": 1,
  "promptBound": true,
  "promptStatus": "a1ttsv2 已并入游戏字段说明；下方为完整游戏输出契约。本轮 ResponseFormat 为空，使用文本输出契约",
  "instruction": "- a1ttsv2：与 content 并列的必填顶层字段。有说出口的对白时返回含 instruct 和非空 segments 的对象…",
  "fieldContract": "## 输出格式\n按下面的 JSON 结构输出…{\"content\":…,\"a1ttsv2\":{\"instruct\":…,\"segments\":[…]}}",
  "example": "{…\"a1ttsv2\":{\"instruct\":\"保持参考声线，吐字清楚，语速适中，平静自然地说完\",\"segments\":[…]}}"
}
```

**结论：MOD 的提示增强是生效的**，它把完整的 a1ttsv2 契约（含字段说明、输出格式、示例）
注入了发给模型的 prompt。我们收到的那份 prompt 里已经有这些内容。

所以之前「59 个样本 0 命中 a1ttsv2」的结论**只对 10-24 那批旧样本成立**——
当时 `TtsMode` 可能还是 v1，MOD 不会注入 v2 契约。现在 `TtsMode = v2`，注入就发生了。

## 二、这次实测的完整管线（48 个事件）

```
capture parsed

```

第 2 轮出现 `cancellation completed — NPC / 场景上下文改变`，

不是配置里 CosyVoice 的 8892。Breeze v2 走独立端口。

## 三、真正的问题找到了：我们改错了字段

模型写的 instruct 直接照抄契约示例：

```
保持参考声线，吐字清楚，语速适中，平静自然地说完
```

**这句话对所有角色都一样** → 所以用户听到「跟 preset 语音差不多」。

而我们的双层词表（`PROFILE_DELIVERY` + `PERFORMANCE_DELIVERY`）只作用在
V1 的 `a1tts_v1` / `voice_style` 上：

```python
for key in ("a1tts_v1", "a1ttsv1", "voice_style", "voiceStyle"):   # ← 没有 a1ttsv2！
```

**a1ttsv2.instruct 我们从来没碰过**，等于两层文字全白做。

## 四、修复：layer_instruct()

新增 `voicebook.layer_instruct()`：把角色基线补到模型那句前面，形成两段式。

```
输入：保持参考声线，吐字清楚，语速适中，平静自然地说完
profile=hard   → 话少干脆，落字有力，语气不绕弯；<原句>
profile=subtle → 语气温和克制，重点轻落，留有余地；<原句>
profile=free   → 轻快松弛，语尾自然，不强加笑声；<原句>
```

规则：
- 模型没写 instruct → 用 `compose(profile, performance)` 兜底
- 已带基线 → 不重复叠加
- 超长 → 保住基线，截断模型那段（尽量断在标点），总额 ≤ 120（官方 schema 上限）
- 开关 `tts_style_v2` 关闭时**完全不动**（函数内也加了门控，防以后被别处直接调用绕过）
