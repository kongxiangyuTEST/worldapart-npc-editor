# 音色不统一的量化诊断（2026-10-28）

用户连续三轮反馈同一类问题：「每段话的音色保持得并不统一」「音色又变了」。
这一份是用 Breeze 实测数据定位到根因的记录，不是推测。

---

## 一、先排除的假设

### 假设 1：逐段独立请求导致音色漂移 → **不成立**

同一句话、同一 instruct、同一参考音，连跑 3 次：

```
run1  5.44s  md5=4e3eba1486d2
run2  5.44s  md5=4e3eba1486d2
run3  5.44s  md5=4e3eba1486d2
```

**md5 完全一致 → 整条链路是确定性的。** 跨请求不会引入任何差异。

（顺带确认 MOD 确实是逐段请求：6 轮对话对应 22 次 `POST /v1/audio/speech`，
每次请求体约 674KB ≈ 参考音 448KB 的 base64 —— 每次都在重新传参考音。）

既然确定性，合并成单段对音色**没有收益**（但对减少请求次数、减少拼接点有用，
所以 `tts_single_segment` 保留默认 true）。

### 假设 2：tag 不稳定 → 不成立

`tag_for(performance)` 对同一轮的所有段填同一个 tag。段间 tag 相同。

---

## 二、真正的根因：instruct 一变，音高就动

固定文本、固定 NPC、固定参考音，只改 instruct：

| instruct | 时长 | 基频 | 相对纯基线 |
|---|---|---|---|
| 纯基线（subtle） | 5.44s | 222.2 Hz | — |
| +句间留半拍 | 5.20s | 217.2 Hz | **-2.27%** |
| +语速放慢 | 5.20s | 216.3 Hz | -2.67% |
| +句尾短促收住 | 5.20s | 214.8 Hz | -3.31% |
| +重音压实 | 5.12s | 213.1 Hz | -4.09% |
| +重点处放慢 | 4.16s | 209.3 Hz | **-5.80%** |
| +闲聊（诱导型） | 4.96s | 227.4 Hz | +2.33% |
| +威胁（原版） | 5.12s | 238.0 Hz | **+7.11%** |

**任何 instruct 变化都会让音高移动 2–7%（最大跨度 14%）。**
人的音高差 7% ≈ 1.2 个半音，足以听成「换了个人」。

### 对照：其他因素的影响幅度

| 变量 | 音高极差 |
|---|---|
| 文本内容不同（同一 instruct） | 5.53% |
| 角色基线不同（同一文本） | 5.57% |
| 表演层不同（同一文本、同一基线） | **8.29%** |

结论很刺眼：

1. **表演层造成的偏移（8.3%）比文本本身的自然起伏（5.5%）还大** —— 它就是「换人感」的主犯。
2. **角色之间的区分度（5.6%）和文本噪声（5.5%）几乎一样大** —— 所以角色差异容易被内容淹没，
   这也解释了为什么柳秀娘（`free` 有明显速度差）一听就分得出，苏倾盏/纪小蝶分不出。

---

## 三、这是个取舍，不是 bug

Breeze 的 instruct 是**生成条件**，不是「风格开关」。条件一变，整段声学统计跟着变。
所以：

- **要音色绝对稳定** → instruct 必须恒定 → 每句话念法一样，情绪全丢
- **要每句情绪不同** → instruct 每轮不同 → 音高在 ±7% 摆动 → 听感像换人

在这个引擎上两者不可兼得（除非改用「instruct 恒定 + 靠标点/句长表达情绪」）。

---

## 四、采取的方案

新增 `tts_instruct_mode`，三档：

| 档位 | instruct 内容 | 音色 | 情绪 |
|---|---|---|---|
| **`profile`（默认）** | 只用角色基线，同一 NPC 每轮**完全一致** | 锁死 | 只有文本语调 |
| `profile_model` | 角色基线 + 模型自写的场景描述 | 会漂 3–7% | 有 |
| `full` | 角色基线 + 我们词表的表演层 | 漂得最多 | 最强 |

实现要点：

- `fill_a1ttsv2(..., with_performance=False)` 默认走「只注入基线」
- `_sl_apply_style_v2` 在 `profile` 档下，把模型自写的 instruct **直接覆盖**为基线
  （模型那句常带「温和笑意」「放轻」，照样会改音高 3–7%）
- 两条路径都锁 → 同一 NPC 无论模型写什么、无论什么情绪，instruct 只有一种

同时把 `PERFORMANCE_DELIVERY` 里 12 条含音色词的描述改写成只谈语速/停顿/重音
（「轻声坦诚」→「语速放慢，句句说完留半拍」等）。这是 `full` 档才用得到的，
但改完偏移从 +8% 降到 ±2–6%，风险更低。

---

## 五、对比音频

| 文件 | 内容 |
|---|---|
| `.tmp_对比_A_每轮带情绪.wav` | 温和句（基线+comfort）+ 强硬句（基线+threat）—— 旧行为 |

---

## 六、还没解决的问题

1. **角色区分度太弱**：角色基线带来的 5.6% 音高差和文本噪声同量级。
   想在多个角色间听出差异，可能得拉大基线差异（比如让不同角色的语速差更极端），
   但那样每个角色会显得更"演"。
2. **`tag` 通道没验证过**：MOD 有 `tag_aware` 分块，tag 理论上能表达情绪而不动 instruct。
   若 tag 真能进 Breeze 且不改音高，那才是"音色稳 + 有情绪"的正解。未测。

## 二、送礼轮静音：MOD 内部缺陷，已定位

第 4 轮（20:38:02）用户听到「出现送礼物的环节，语音就没了」。

### 证据链

BepInEx 日志（`LogOutput.log`）：

```
TTS-V2 task-result npc=npc:100000 round=22 chars=960 a1ttsv2=valid     ← 台本拿到了
TTS-V2 recovery  npc=npc:100000 round=0  result=round_unavailable effective=absent
Stage3 AddNpcChatMessage mapped a1ttsv2=absent recovered=unparseable effective=absent
TTS-V2 not-submitted ... reason=缺少有效 a1ttsv2 台本，未从正文补写
```

正常轮长这样：

```
TTS-V2 task-result npc=npc:100000 round=21 chars=789 a1ttsv2=valid
TTS-V2 recovery  npc=npc:100000 round=21 result=task_result effective=valid
Stage3 AddNpcChatMessage mapped a1ttsv2=absent recovered=valid effective=valid
```

### 机制

MOD 在 `AddNpcChatMessage` 阶段要靠「轮次编号」去找自己缓存的台本：

1. `round` 有效 → 取缓存 → 出声（`result=task_result`）
2. `round` 丢失（变 0）→ 只能退化去解析游戏归一化后的文本
   → 那份文本已被 `CopyIfPresent` 白名单洗掉 a1ttsv2 → `unparseable` → 静音

送礼那轮游戏走了另一条调用路径，没把 `promptTurnId` 带过来，于是 round=0。

### 统计（108 轮全部历史）

| 指标 | 值 |
|---|---|
| 总轮次 | 108 |
| 静音轮次 | **2** |
| 静音发生场景 | **都是 NPC 送礼**（12:05 纪小蝶、12:38 苏倾盏） |
| 静音轮 rawLength | 437 / 413（成功轮平均 380、最大 1519）→ **与长度无关** |

### 已排除的我们这边的原因

- 不是台本没写：那轮 `a1ttsv2Status=valid`、`chars=143`
- 不是重复判定：`isRepeated=False`
- 不是长度超限：`MaxRecordChars=120000`，且成功轮更长
- 不是我们改了 intent/gift 结构：core_proxy 对 intent 只做 setdefault

### 结论

**这是 MOD 的内部缺陷，代理侧无法修复。** 能做的：

1. 让用户看得见（已做：编辑器「MOD 诊断」新增「逐轮出声结果」+「静音原因」）
2. 想要彻底解决只能等 MOD 作者修，或改 MOD 的 DLL（风险高，不做）

## 三、编辑器诊断增强

`editor.py` 新增 `mod_diag_errors()`，数据源是 `BepInEx/LogOutput.log` 尾部 +
`.state/tts-diagnostics/last-error.json`，解析出每轮的
`round / result / effective`，并把 `round_unavailable` 翻译成中文解释。

前端（`web/speech.js`）在 MOD 诊断卡片里追加两块：

```
! 最近 15 轮里有 1 轮没出声（下面标红的那几行）
逐轮出声结果（MOD 恢复日志）
✓ 第 18 轮　valid
...
✗ 第 ? 轮　absent　round_unavailable        ← 送礼那轮
本轮取不到对话编号，MOD 拿不到缓存台本 → 静音。实测集中在 NPC 送礼那轮…
```

这样以后遇到静音，第一时间能分清是「台本没到」还是「MOD 自己丢了编号」。

# 附二：原版对照实验（2026-10-28 21:00）—— 确认是 MOD 的锅

## 实验设计

用户主动提出「去测原来 MOD 的礼物数据」。做法：把我们的干预全部关掉，
只做纯转发，让 MOD 只能拿到模型自己写的台本。

```
tts_autofill       False   ← 不从正文补台本
tts_style_v2       False   ← 不改 instruct、不合并分段
tts_script_v2      False
tts_style_inject   False
```

## 结果

| 时间 | 玩家 | 回复字数 | 台本状态 | 出声 |
|---|---|---|---|---|
| 12:52:37 | 镇长我有点伤能帮帮我吗 | 17 | **absent**（模型自己没写） | ✗ 预期内 |
| 12:53:12 | （手臂的血开始缓缓流出） | 270 | valid | **✓ reply-000033** |
| 12:54:17 | 刚刚有无名之人想要害我… | 317 | **valid** | ✗ `round=0 round_unavailable` |

第三轮就是用户说的「好感度属性增加时没语音」那轮。

**台本明明 valid，MOD 自己判 absent → 静音。**

日志：

```
TTS diagnostic NPC reply hook fired npc=npc:100111 messageChars=317 rawChars=497
TTS-V2 recovery npc=npc:100111 round=0 result=round_unavailable effective=absent
Stage3 AddNpcChatMessage mapped a1ttsv2=absent recovered=unparseable effective=absent
TTS-V2 not-submitted ... reason=缺少有效 a1ttsv2 台本，未从正文补写
```

## 结论

**与我们无关。** 原版条件下（我们不补台本、不改 instruct），
游戏触发特殊事件（送礼、好感度变化）时 MOD 同样丢轮次编号 → 静音。

至此三次静音全部同型：

| 时间 | 场景 | 台本状态 | MOD 结果 |
|---|---|---|---|
| 12:05:28 | NPC 送礼（纪小蝶） | valid | round=0 round_unavailable |
| 12:38:02 | NPC 送礼（苏倾盏） | valid | round=0 round_unavailable |
| 12:54:17 | 好感度变化（100111） | valid | round=0 round_unavailable |

共 110 轮 3 次，约 2.7%。

## 另一个新发现的失败类型

12:52:37 那轮 `result=early_observation`（round=24）—— MOD 认为这是
「早期观察」而非正式回复，不朗读。那轮台本也是 absent（模型回了一句 17 字的短话，
没写台本），所以静音是合理的。

## 副产品：模型自己写台本的比例

原版模式下 3 轮里只有 1 轮（12:52）模型没给台本，另两轮都自己写了 valid 的台本。
说明 MOD 的契约注入是有效的，`tts_script_v2` 保持关闭是合理的
（我们的兜底只在模型漏写时补，实际很少触发）。

## 应对

代理侧无法修复（拿不到播放接口）。可选：

1. **接受**（推荐）：约 2.7%，只影响那一轮的声音，文字正常显示，下一轮恢复
2. 抑制送礼：让 `give_gift` 恒为 false —— 能消掉送礼那两次，**但好感度那次消不掉**
   （好感度是游戏核心机制，无法抑制）

所以即使抑制送礼，也消不干净。建议接受，并把原因展示在编辑器诊断里（已做）。

# 附三：完全透传复测（2026-10-28 21:05）—— 结论封锁

## 实验设计（比附二更严）

附二只是关掉了「补台本 / 改 instruct」，但名片、长期记忆、注入语、替换规则仍在改 prompt。
这次启用 `proxy_passthrough`，**入口出口全不加工**：

| 位置 | 行为 |
|---|---|
| 入口 `prepare_messages` | 不改 system，不注入名片/记忆/注入语，不套替换规则 |
| 出口 `chat_completions` | 上游原始响应一个字节不改直接返回：不包装结构、不补台本、不改 instruct |

等价于「这台中转不存在」。

## 结果

用户实测反馈：**「确实不关中转的问题，原 mod 就是没有语音在读取送礼物加好感度的时候」**

即：完全原版条件下，游戏在「送礼 / 好感度增加」这两类事件上本来就不出声。

## 最终定论

| 项 | 结论 |
|---|---|
| 静音是否由我们造成 | **否**。三份对照（正常 / 只关台本 / 完全透传）结果一致 |
| 触发条件 | 游戏的特殊事件流程（送礼、好感度变化） |
| 机制 | MOD 在 `AddNpcChatMessage` 阶段取不到轮次编号（`round=0` → `round_unavailable`），
拿不到缓存台本；退化去解析游戏归一化后的文本，那份已被白名单洗掉 → `unparseable` → 静音 |
| 我们能否修 | **不能**。代理拿不到播放接口，也无法干预 MOD 内部 |
| 频率 | 约 3/110 ≈ 2.7% |

## 配置已恢复

```
proxy_passthrough    False
tts_autofill         True
tts_style_v2         True
tts_script_v2        False
tts_instruct_mode    profile
tts_single_segment   True
tts_instruct_override ''
```

## 保留的工具

`proxy_passthrough` 与 `tts_autofill` 都留着了（默认关/默认开），
以后再遇到「怀疑是代理造成的」问题，可以一条配置切过去做对照，不用改代码。

编辑器「MOD 诊断」页会把 `round_unavailable` 直接标红并解释，
以后看到静音不用再排查一遍。

# 附四：升级 0.8.2 后的复测（2026-10-28 21:35）

## 一、升级过程

工坊包 `3817030666` 已经是 0.8.2，但 Steam 只下载不安装，要手动跑 `安装.bat`。

| | 0.8.1 | 0.8.2 |
|---|---|---|
| DLL | 7,853,056B | 7,923,200B |
| a1ttsv2 契约 | 5,304B | **7,434B**（扩展了，可能是 V3） |
| cfg 键数 | 35 | **56**（新增 21 个） |

安装器行为（已核实 `Install.ps1`）：config / references / models **全部跳过**，
只覆盖程序文件。`component.txt = Program`，所以不碰任何 cfg 键。
→ 用户设置、参考音、模型全都保留。备份在 `.backup/mod-0.8.1/`。

## 二、0.8.2 新增的两套机制（从界面文案还原）

```
台本生成方式
  V1 随文返回    结构清晰 · 可能漏读。部分 Mod 可能移除语音台本
  V2 分开返回    格式复杂 · 容错较低
  V3 单独生成    减少干扰 · 增加消耗。游戏先生成对话，再独立请求 AI 生成语音台本

缺失补全（[VoiceCompletion]）
  缺少台本，自动补齐。使用下方 API，每条最多多请求一次，
  会增加 token 消耗和等待时间。开场白命中预设时直接使用。

台本 API（V2 补全与 V3 共用）
  跟随游戏自定义 API ← 实测 scriptApi=follow_game，会打到我们代理
```

配置项：`VoiceCompletion.*` 14 个键 + `VoiceScripts.IndependentGeneration`。

## 三、两次实测，两条路都堵

### 第一次：V2 + 补全关（0.8.2 默认）

普通轮 2 轮正常（`task_result valid`），送礼轮照样：

```
TTS-V2 recovery round=0 result=round_unavailable effective=absent
```

**与 0.8.1 完全一样。** 0.8.2 没修这个场景。

### 第二次：开 V2 补全（`VoiceCompletion.Enabled=true`）

补全**根本没触发**。原因：补全管的是「模型没写台本」，
而这一轮 `a1ttsv2Status=valid`（台本有），挂的是后面「按轮次取缓存」。

### 第三次：开 V3（`IndependentGeneration=true`）

V3 确实生效了（日志 `generation=v3_independent`），台本也生成了
（`task-result round=1 chars=728 a1ttsv2=valid`），但被另一个门槛拦住：

```
TTS script skipped round=0 reason=admission_rejected
    roundFound=True independent=True roundSpeak=True
    latestRound=False epochMatch=True alreadySubmitted=False
```

**`roundFound=True` —— V3 把「找不到轮次」解决了。**
**但 `latestRound=False` —— 这一轮被判为「不是最新的一轮」，仍然拒收。**

推测：送礼 / 好感度变化时游戏会插入事件并推进内部轮次，
你刚说的那句就变成「旧轮」。MOD 的设计是「只念最新一轮，避免念过期内容」，
正好把这类事件轮挡在门外。

## 四、最终结论

| 版本/模式 | 送礼轮结果 | 门槛 |
|---|---|---|
| 0.8.1 V2 | 静音 | `round_unavailable`（找不到轮次） |
| 0.8.2 V2 | 静音 | 同上，未改善 |
| 0.8.2 V2 + 补全 | 静音 | 补全不覆盖此场景 |
| 0.8.2 V3 | 静音 | `admission_rejected`（轮次被判过期） |

**代理侧无解。** 三条路都试过了，问题不在中转、不在台本，在 MOD 的轮次准入逻辑
与游戏的事件流程冲突。

V3 已关闭（它只多花钱和延迟，不解决静音）。

## 五、0.8.2 留下的好处

1. **诊断日志更详细**：新增 `request-begin` / `TTS script skipped ... reason=...`，
   能直接看到拒绝原因和各个判定字段（`roundFound` / `latestRound` / `epochMatch`），
   比 0.8.1 只有 `result=xxx` 强很多
2. **普通轮更稳**：0.8.2 下连续 2 轮都是 `task_result`，没有杂音
3. **多一层兜底**：`VoiceCompletion` 保留开启，模型漏写台本时能补（成本低）

## 六、当前配置


# 附五：触发条件的补充理解（2026-10-28 21:37，用户观察）

之前把静音场景统称为「送礼 / 好感度变化」，用户的观察比这个更准确：

> 这个问题很大概率是因为**玩家诱导 NPC 要礼物**这么触发的，并不是 NPC 主动想给的，
> 所以就没给到，但实际上还是归为送礼物这一行为。

也就是说，即使 `intent.give_gift` 不成立（礼物没结算、好感度没加），
对话里一旦出现「赠礼」的语义，游戏内部仍会推进事件轮次，
那句回复就变成「旧轮」→ MOD 判 `latestRound=False` → 静音。

**两个现象同源**：礼物没到手 + 语音没出声，都是「玩家索要而 NPC 没真的给」导致的。

对使用的启示：这是玩家行为触发的，**不主动索要礼物就基本不会撞上**。
不需要为它做任何代码改动。
