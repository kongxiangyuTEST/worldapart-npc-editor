# 酒馆（SillyTavern）三件套与我们项目的对接分析

2026-10-30。**先分析、后动手**：文末的导出工具已经可用，导入/世界书/预设还是空白。

---

## 0. 一句话结论

| 资产 | 结构复杂度 | 我们能不能做 | 现状 |
|---|---|---|---|
| 角色卡（Character Card V2，PNG 里嵌 JSON） | 低：纯 JSON + base64 + PNG tEXt 块 | **能，已实现** | `tools/tavern_card.py`，1592 张可批量导出，往返不丢字段 |
| 世界书（World Info / Lorebook） | 中：条目数组 + 触发关键词 + 插入位置/深度 | 能，但要先定「哪些内容该做成条目」 | 未做 |
| 预设（Preset） | 中：采样参数 + 提示词条目数组 + 顺序表 | 能导出，但语义对不上（见 §3） | 未做 |

三者里只有角色卡是「无损搬运」；另外两个是**语义迁移**，会丢东西，得先想清楚丢哪部分。

---

## 1. 角色卡：数据结构

酒馆的角色卡就是一张 **PNG**，`tEXt` 块里塞了 `chara` + base64(JSON)。JSON 遵循公开的 Character Card V2 规范：

```json
{
  "spec": "chara_card_v2",
  "spec_version": "2.0",
  "data": {
    "name": "苏倾盏",
    "description": "身份/背景/外貌，自由文本",
    "personality": "性格摘要，自由文本",
    "scenario": "对话发生的场景",
    "first_mes": "开场白（角色说的第一句）",
    "mes_example": "<START>\n{{user}}: …\n{{char}}: …",
    "creator_notes": "作者备注，模型看不到",
    "system_prompt": "覆盖全局 system",
    "post_history_instructions": "插在历史之后、生成之前",
    "alternate_greetings": ["备选开场白"],
    "tags": ["标签"],
    "creator": "作者",
    "character_version": "1.0",
    "extensions": { "…任意自定义…" },
    "character_book": { "entries": [ …世界书… ] }
  }
}
```

**PNG 侧的坑**（都已踩过并解决）：

1. 块顺序：`chara` 必须插在 IHDR 之后，CRC 用 `zlib.crc32(type + data)` 重算。
2. 关键字有两个：老客户端读 `chara`，新版本还认 `ccv3`。我们只写 `chara`，读取时两个都试。
3. 底图不是必须的——但没有图就没有 PNG，只能给 JSON。本项目用 `web/portraits/<npc_id>.png`；没有头像时用 PIL 生成占位卡（**字体必须指定系统中文字体**，PIL 自带位图字体没有汉字，否则名字全是方块）。

---

## 2. 我们的 md ↔ 角色卡字段

| `editor_cards/<id>-<名>.md` | V2 字段 | 说明 |
|---|---|---|
| `# 名字` / `- 姓名` | `data.name` | |
| `## 预设资料` 的条目 | `data.personality` | 拼成「性别：女；年龄：28；…」一行 |
| `## 原游戏背景` | `data.description` | 唯一的大段背景，正好对得上 |
| `## 用户名片` | `data.system_prompt` | 我们的人设补充层，语义最接近 system |
| `- 个性` / `- 性别` | `data.tags` | 便于酒馆里筛 |
| `NPC ID` | `data.extensions.wa_npc_id` | 回导时靠它定位角色 |
| 预设资料原始字典 | `data.extensions.wa_attrs` | 酒馆不用，回导时原样还原，保证无损 |

**故意留空的三个**：`scenario` / `first_mes` / `mes_example`。
游戏里的台词是模型按剧情动态生成的，我们没有「开场白」这种东西；硬编一句等于造假，不如留空让使用者自己填。

## 3. 预设（Preset）：能导出，但语义对不上

酒馆的「预设」是**采样参数 + 提示词编排**，两份文件：

- Chat Completion 预设：`temperature / top_p / frequency_penalty / presence_penalty / openai_max_tokens / prompts[] / prompt_order[]`
- Text Completion 预设：额外的 `instruct` 模板、`names_behavior`、`stop` 序列等

我们这边对应的只有 `ai_config.json` 里的采样参数（当前几乎全是默认）+ 注入语/替换规则。问题是：

| 酒馆概念 | 我们这边 | 能不能搬 |
|---|---|---|
| `prompts[]`（可拖顺序的提示词块：主提示/人设/世界书/示例/越狱…） | system 拼装是 core_proxy 代码写死的 | ❌ 搬不过去，除非把拼装逻辑数据化 |
| `prompt_order[]` | 同上 | ❌ |
| 采样参数 | 上游请求里直接带 | ✅ 能导出成「建议值」，但没有一键导入的入口 |

**结论（2026-10-30 更新）**：需求只要**导出**、不要导入，所以不做「数据化重构」，
改用一张固定的层表直接生成 preset —— `tools/tavern_export.py`：

- `preset-worldapart.json`：9 个块（`main` / `inject_prefix` / `worldInfoBefore` / `charDescription` / `charPersonality` / `personaDescription` / `chatHistory` / `user_card` / `jailbreak`）+ `prompt_order`，把「注入语在最前、名片在最后」这条权重关系保留下来
- `worldbook-worldapart.json`：注入语 → 一条 `constant: true` 常驻条目；`lorebook.json` 有内容就一并转成关键词条目（目前该文件是空的，所以只有 1 条）

**两个必须写进说明的限制**：
1. **采样参数是酒馆默认值**，不是我们调过的值 —— `ai_config.json` 里根本没有 temperature/top_p（请求参数由游戏给）。
2. **注入语默认不导出正文**（含成人向内容），要带得显式加 `--with-inject`，避免误把敏感文本打进分享物。

导入方向只保留「酒馆卡 → md」这一条（`tavern_card.py import`），预设与世界书不做反向解析。

## 4. 世界书（Lorebook）：最值得做的下一个

结构（`character_book` 或独立 `.json`）：

```json
{
  "entries": [{
    "keys": ["河望镇", "客栈"],
    "secondary_keys": [],
    "content": "河望镇是……",
    "constant": false,          // true = 常驻，不靠关键词触发
    "selective": true,
    "insertion_order": 100,
    "position": "before_char",  // 或 after_char / at_depth
    "depth": 4,                 // position=at_depth 时插进历史第 N 条
    "probability": 100,
    "case_sensitive": false,
    "enabled": true
  }]
}
```

对我们的三种内容，映射关系其实很清楚：

| 我们的内容 | 世界书形态 | 为什么合适 |
|---|---|---|
| 游戏设定/地理/门派（`原游戏背景` 之外的世界信息） | 关键词触发的普通条目 | 本来就该「提到才注入」 |
| 注入语（`ai_config.inject`，495 字） | `constant: true` 的单条，`position: before_char` | 常驻、每轮都在，与现在行为一致 |
| 长期记忆（`memory/*.json` 的过往要事） | `at_depth` + `depth: 4` 的条目 | 语义上就是「插进最近历史里」，比我们现在的 append 更贴 |

**但注意**：世界书是酒馆的调度逻辑，我们的 core_proxy 不认这套 JSON。所以「导出世界书」只是**给别的工具用**（比如让用户在酒馆里接着聊同一个角色），不会反过来影响游戏内注入。

要做的话顺序应该是：先「导出」（只读搬运）→ 再考虑「core_proxy 读世界书当注入源」（那才是真打通，但要重写注入层）。

## 5. 已实现的工具：`tools/tavern_card.py`

```bash
python tools/tavern_card.py export 100000           # 单张 → JSON + PNG
python tools/tavern_card.py export --all -o out/    # 1592 张批量
python tools/tavern_card.py import 卡.png -o editor_cards   # 酒馆卡 → md
```

- 纯标准库做 PNG 读写（`struct` + `zlib` + `base64`），只有占位底图用到 PIL
- **往返无损**：`wa_attrs` 存原始属性表，导回来还是「- 性别：女 / - 年龄：28 / …」
- 已验证：`100000 苏倾盏`（无头像 → 占位图）与 `111 焚天宗`（有头像 → 直接用头像）都能导出，PNG 里读回 JSON、再转回 md，字段一致
- 限制：只写 V2；不处理 `ccv3` 的新字段；不导出世界书

---

## 6. 风险与边界

1. **版权**：角色卡里是别人游戏的角色设定与头像。自己导出自己用没问题，**别打包进分享包/发布包**（与本项目「敏感内容隔离」同一条规矩）。
2. **规范会变**：酒馆主力已支持 v3（`ccv3` 块、更多 `extensions`），我们写 V2 是兼容性最稳的选择；读的时候两个关键字都试，写只写 V2。
3. **别把酒馆当目标**：我们的目标是在游戏里生效，酒馆格式只是「导出便于外部分享/复用」。真要做世界书驱动注入，等于重写注入层，得另开一轮评估。
